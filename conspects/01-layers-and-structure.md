# Основные принципы и правила архитектуры

## Разделение на слои View и Presenter

- **View** — это только JSX (отображение). Компонент не должен содержать никакой JS‑логики, кроме импорта хука `usePresenter`.
- **Presenter** — прослойка, которая извлекает и подготавливает данные для отображения (например, забирает данные из Redux и форматирует их для JSX). Логику выносят в отдельные хуки (например, `useSuggestions` для загрузки опций автокомплита).

## Ограничение размера файлов (правило 120 строк)

Чтобы код оставался читаемым и поддерживаемым, ни один файл не должен превышать **120 строк**. Это вынуждает разбивать логику на более мелкие абстракции и файлы, что упрощает навигацию и внесение изменений. На практике это правило даже улучшило качество кода в команде из 20 разработчиков.

## Древовидная структура папок

Файловая структура должна отражать иерархию компонентов на экране.

- Каждый компонент имеет свою папку, где лежат его view и presenter.
- Если компонент используется только внутри другого компонента, его папку размещают внутри папки «родителя». Так формируется дерево вложенности, которое может достигать 10–15 уровней (как в мессенджере) без потери ясности.

**Пример:** компонент `Messenger` → внутри него `Chats` и `ActiveChat` → внутри `ActiveChat` есть `BottomPanel` → внутри неё `StickerPackIcon` и т. д.

## Работа с переиспользуемыми компонентами

- Для компонентов, которые используются во многих местах (например, инпуты, модальные окна), создают глобальную папку `components`.
- Для компонентов, переиспользуемых только в рамках определённой части дерева (например, типы сообщений в списке), можно создавать промежуточные папки `components` на любом уровне вложенности. Это упрощает удаление/рефакторинг частей проекта: если удалить ветку дерева, вместе с ней уйдут и специфичные для неё переиспользуемые компоненты.

# Практические приёмы и примеры

## Выделение логики в хуки

Вместо того чтобы держать всю логику в одном компоненте, её разбивают на мелкие хуки с понятными названиями (`useSuggestions`, `usePresenter` и т. п.). Это делает код читаемым, как оглавление книги: сначала видишь абстракции, а детали скрываются внутри.

## Пример с автокомплитом

В изначальном коде вся логика (обработка ввода, debounce, загрузка опций, обработка клика) была в одном компоненте. После применения архитектуры:

- `view.jsx` содержит только JSX и импорт `usePresenter`;
- логика загрузки опций вынесена в `useSuggestions`;
- общая логика управления состоянием — в `usePresenter`.

Это позволяет легко добавлять новые функции (например, обработку race conditions или клиентскую валидацию языка) в соответствующие хуки, не превращая компонент в «кашу».

## Именование файлов

Есть два подхода к именованию файлов View:

- `index.jsx` — удобно для импорта, но все компоненты имеют одинаковое имя, что усложняет навигацию в IDE.
- Имя файла совпадает с именем папки (например, `autocomplete.jsx` в папке `autocomplete`) — лучше для поиска и навигации, но импорт выглядит менее лаконично.

В рамках курса студентам разрешено выбирать любой из подходов для домашних заданий.

# Важные мысли и выводы

- **«Людям лень писать хорошо».** Без жёстких правил (вроде лимита в 120 строк) разработчики склонны писать большие файлы с кучей логики, потому что это быстрее на этапе создания. Но в долгосрочной перспективе это сильно усложняет поддержку. Правило заставляет преодолеть «этап отрицания» и выработать полезную привычку.
- **Архитектура — это абстракции, а не инструменты.** Хороший архитектор мыслит в терминах абстракций (слои, ответственность, разделение), а не конкретных библиотек или фреймворков. Поэтому описанный подход можно адаптировать под React, Angular, Vue и другие технологии.
- **Практика обязательна.** Без реальных задач (домашних заданий) усвоить нюансы архитектуры невозможно: только при попытке применить правила на практике возникают вопросы, которые помогают глубже понять материал.
