# Правила архитектуры

Этот проект посвящён архитектуре, а не коду. Правила ниже обязательны для любого изменения. Если задачу нельзя решить по правилам, сначала обсуждаем правило, а не обходим его.

Источники: конспекты из [`conspects/`](conspects/). Новые правила после каждого урока добавляются сюда.

## 1. Слои

Слои образуют VIPER: View, Interactor (у нас — Task), Presenter, Entity, Router.

**1.1. View — только JSX.** View отвечает только за отображение. Единственная логика в нём — вызов хука `usePresenter`. Что ещё допустимо в JSX (`.map()`, условный рендер, ранний выход), уточняет правило 8.4.

**1.2. Presenter — прослойка между данными и View.** Presenter извлекает данные из хранилища и готовит их к отображению. View получает готовые значения и обработчики. Presenter знает, на какое событие какую задачу вызвать: это мост между интерфейсом и бизнес-логикой.

**1.3. Логика живёт в хуках с понятными именами.** Presenter не должен разрастаться: отдельные задачи выносятся в отдельные хуки, например `useSuggestions`. Код читается как оглавление книги: сначала абстракции, детали скрыты внутри.

**1.4. Task — вариант использования, слой бизнес-логики.** Вся бизнес-логика приложения живёт в задачах (правила раздела 7). Сценарий не обязан быть бизнес-правилом в узком смысле: «перейти на следующую страницу» и «выбрать жанр» — тоже задачи, если у действия есть шаги (обновить стор, загрузить данные, откатить при ошибке). На вопрос «бизнес это или нет» не отвлекаемся.

**1.5. Entity — хранилище.** Сущность — это данные и методы их обновления. Её роль играет стейт-менеджер.

**1.6. Router — навигация делается в Presenter.** Навигация зависит от среды (браузер, мобильное приложение), а не от бизнеса, поэтому в задачи она не попадает.

## 2. Размер файлов

**2.1. Не больше 120 строк в любом файле кода.** Если файл не помещается в лимит, его разбивают на более мелкие абстракции. Исключений для кода нет.

**2.1.1. Документация (`.md`) под лимит не попадает.** Правила, конспекты и инструкции пишем так подробно, как нужно, и не ужимаем ради числа строк. Biome не применяет к Markdown правило о числе строк, но форматирует его (например, выравнивает таблицы), поэтому перед коммитом `.md` тоже прогоняем `npm run check:fix`.

## 3. Структура папок

**3.1. Дерево папок повторяет иерархию компонентов на экране.**

**3.2. У каждого компонента своя папка**, в которой лежат его View и папка `logic`. Если логики у компонента нет, папки `logic` тоже нет (правило 8.5).

**3.3. Компонент, используемый только внутри другого компонента, лежит в папке родителя.** Глубина вложенности не ограничена: 10–15 уровней — это нормально.

```text
Messenger/
├── Chats/
└── ActiveChat/
    └── BottomPanel/
        └── StickerPackIcon/
```

**3.4. Вся JS-логика компонента лежит в папке `logic`:** presenter, все хуки и вспомогательные функции Presenter'а, которые хуками не являются (например, форматирование: `ShowCard/logic/formatShow.ts`). Задачи компонента — в `logic/tasks`.

**3.5. Задача в `tasks` — это файл или папка.** Папка нужна, когда задачу приходится разбить на несколько файлов, чтобы уложиться в 120 строк.

```text
LogoutButton/
├── LogoutButton.tsx
└── logic/
    ├── usePresenter.ts
    └── tasks/
        ├── logout.ts
        └── unsubscribeFromPush/
```

## 4. Переиспользуемые компоненты и задачи

**4.1. Компонент, нужный во многих местах приложения, лежит в глобальной папке `components`.** Например, инпуты и модальные окна.

**4.2. Компонент, переиспользуемый только в одной ветке дерева, лежит в промежуточной папке `components` этой ветки.** Такая папка допустима на любом уровне. При удалении ветки вместе с ней уходят и её компоненты.

**4.3. В `components` не может лежать компонент, который импортируется лишь единожды,** чтобы не складировать туда что угодно. Такой компонент лежит в папке своего родителя (3.3). Правило не из конспекта, это наше уточнение к 4.1–4.2.

**4.4. Задачи раскладываются по тем же правилам, что и компоненты.** Переиспользуемая задача лежит в глобальной папке `tasks`, а задача, нужная одному компоненту, — в его `logic/tasks`.

## 5. Именование

**5.1. Файл View называется так же, как его папка:** `SearchBar/SearchBar.tsx`.

**5.2. Файл Presenter называется `usePresenter.ts`:** `SearchBar/logic/usePresenter.ts`.

**5.3. Задача называется глаголом:** функция `logout` в файле `logout.ts`, `addUser`, `searchShows`.

**5.4. Функция `api/` называется по транспортному действию, задача — по сценарию:** `fetchShows` в `api/` и `searchShows` в `tasks`, `postLogout` и `logout`. Так имена не сталкиваются в одном импорте, а по имени сразу видно слой.

## 6. Принципы

**6.1. Архитектура — это абстракции, а не инструменты.** Решения формулируем через слои и ответственность, а не через конкретные библиотеки.

**6.2. Правила не ослабляем ради скорости.** Большой файл быстрее написать, но дороже поддерживать.

**6.3. Правила проверяем практикой.** Вопрос, возникший при применении правила, обсуждаем и фиксируем здесь.

## 7. Задачи (tasks)

Задача — это вариант использования (use case) из «Чистой архитектуры»: то, что пользователь просит приложение сделать. «Найти сериал», «выйти из аккаунта», «купить товар». Именно этот слой обычно называют бизнес-логикой. Его можно описать словами, не упомянув ни одного инструмента, и так же его нужно писать в коде.

Как задача выглядит на фоне остальных слоёв:

```text
View ──событие──▶ Presenter ──вызов──▶ Task ──▶ Entity (стор)
                     ▲                   │  └─▶ api/
                     └────результат──────┘
```

**7.1. Задача — обычная функция.** У варианта использования три части: ввод, порядок действий, вывод. Это ровно параметры, тело и `return`. Задача не thunk, не сага, не хук, не класс и не метод стора.

_Почему:_ обычную функцию можно вызвать откуда угодно, дождаться через `await`, получить из неё результат и протестировать без окружения. Любая обёртка над ней добавляет ограничения, а взамен ничего не даёт.

**7.2. Одна задача — одна функция снаружи.** Внутри её можно разбить на сколько угодно мелких функций (и файлов, правило 3.5), но вызывающий видит один вызов. Самостоятельный кусок, нужный в разных сценариях, выносится в отдельную задачу и вызывается из этой как обычная функция.

```ts
// logic/tasks/logout.ts
export async function logout(): Promise<LogoutResult> {
  await unsubscribeFromPush(); // отдельная задача: нужна и в других сценариях
  const result = await api.logout();
  if (!result.ok) return { error: result.error };

  userStore.clear();
  chatsStore.clear();
  return { error: null };
}
```

_Почему:_ тело задачи читается как описание сценария: отписаться от пушей, выйти на сервере, почистить данные. Детали (Safari, Service Worker, уже выключенные пуши) спрятаны во вложенной задаче.

**7.3. В задаче нет React.** Ни хуков, ни JSX, ни импортов из `react`, ни компонентов. Слой не зависит от библиотеки отображения.

_Почему:_ бизнес-логика переживает смену фреймворка. Если переписать проект на Angular или Vue, переписываются View и Presenter, а задачи остаются почти без изменений. Это и есть правило 6.1 на практике.

_Проверка:_ если в задаче понадобился хук, значит этот кусок относится к Presenter. Задача получает из Presenter готовые значения параметрами.

**7.4. Со стором задача работает напрямую:** импортирует экземпляр стора и вызывает его методы. Библиотеки-посредники (redux-thunk, redux-saga и подобные) не используем.

```ts
import { userStore } from "../../stores/UserStore";

userStore.clear(); // MobX: метод экземпляра
// Redux: store.dispatch(...), store.getState()
// Zustand: useUserStore.getState(), useUserStore.setState(...)
```

_Почему:_ все популярные стейт-менеджеры описывают работу со стором вне компонентов в своей документации, это штатный способ. `store.dispatch` — та же функция, что возвращает `useDispatch`. Посредники вроде thunk нужны лишь для доступа к `dispatch` и `getState`, а взамен запрещают `await` и возврат результата.

**7.5. Задача возвращает результат вызывающему.** Presenter дожидается задачи через `await` и по результату решает, что показать: ошибку, редирект, новое состояние кнопки.

```ts
// logic/usePresenter.ts
export function usePresenter() {
  const [isLoading, setIsLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);
  const navigate = useNavigate();

  const handleClick = async () => {
    setIsLoading(true);
    const result = await logout();
    setIsLoading(false);

    if (result.error) return setError(result.error);
    navigate("/login"); // навигация — в Presenter, правило 1.6
  };

  return { isDisabled: isLoading, error, handleClick };
}
```

_Почему:_ загрузка и ошибка одного действия нужны только этому компоненту. Если прокручивать их через стор, появляются лишние поля, экшены, флаги «действие прошло успешно», эффекты, которые на них реагируют, и очистка стора при размонтировании. Локальное состояние в Presenter исчезает вместе с компонентом само.

_Граница:_ в стор кладём то, что нужно нескольким компонентам. Результаты поиска читают и список, и фильтр, и пагинация, поэтому они в сторе. Состояние кнопки «Выйти» нужно только кнопке, поэтому оно в Presenter.

**7.6. С внешним миром задача говорит через абстракцию.** Запрос к серверу — это вызов функции из `api/` (`fetchShows(query, signal)`, имя по правилу 5.4), а не `fetch` в теле задачи. Задача не знает, HTTP это или веб-сокеты, как устроено тело запроса и куда кладётся токен.

_Почему:_ задача зависит от смысла («найти сериалы»), а не от способа доставки. Если поменяется транспорт или API, исправится один файл в `api/`, а задачи останутся прежними. Направление зависимостей подробно разберём в следующих уроках.

**7.7. Чего в задаче быть не должно** (сводка правил выше):

- React: хуков, JSX, компонентов (7.3);
- навигации: это Presenter (1.6);
- `fetch` и деталей транспорта: это `api/` (7.6);
- подготовки данных к отображению (форматирования, классов, aria-атрибутов): это Presenter (1.2);
- запуска по реакции на изменение стора: связь пишется явным вызовом (7.8).

**7.8. Сменил параметр — вызови загрузку.** Задача, которая меняет данные для запроса, сама вызывает задачу загрузки: `goToPage` ставит страницу и вызывает `loadShows`, `selectGenre` ставит жанр и вызывает `loadShows`. Реакции на изменение стора (`useEffect` по полю, `reaction`, `autorun`) для запуска сценариев не используем.

```ts
// Pagination/logic/tasks/goToPage.ts
export async function goToPage(page: number): Promise<LoadShowsResult> {
  const nextPage = Math.min(Math.max(page, 1), searchStore.result.pageCount);
  if (nextPage === searchStore.page) return { error: null };

  searchStore.setPage(nextPage);
  return loadShows();
}
```

_Почему:_ причина и следствие лежат в одной функции. Её можно прочитать сверху вниз, дописать в неё шаг (лог, тост, откат), дождаться через `await` и протестировать без React. При реакции на стор связь «сменил страницу → загрузил» видна только тому, кто знает про эффект в другом конце дерева.

**7.9. Optimistic UI и откат — в задаче.** Если реакция должна быть мгновенной, задача сначала меняет стор, потом вызывает `api/`, а при ошибке возвращает стор в прежнее состояние и отдаёт код ошибки. Что показать в ответ (тост, текст), решает Presenter по результату (7.5, 8.10).

```ts
async function removeFavorite(show: Show): Promise<ToggleFavoriteResult> {
  const index = favoritesStore.indexOf(show.id);
  favoritesStore.remove(show.id);
  try {
    await deleteFavorite(show.id);
    return { error: null, isFavorite: false };
  } catch (error) {
    favoritesStore.insert(index, show); // откат на прежнее место
    return { error: toErrorCode(error) };
  }
}
```

_Почему:_ изменение и его откат — две половины одного сценария, и они должны лежать рядом. Presenter не знает, что было в сторе до клика, а стор не знает, что изменение предварительное.

## 8. Применение в этом проекте

Эти пункты не из конспекта: они уточняют правила под наш стек.

**8.1. Хранилище — MobX.** Конспект говорит о Redux, у нас его роль играют MobX-сторы. Читать стор могут Presenter и задачи, но не View. Менять стор — задачи. Presenter вызывает метод стора напрямую, только если это одно присваивание без последствий: `searchStore.setQuery(value)` на каждый символ ввода. Если у действия есть имя-сценарий («перейти на страницу», «выбрать жанр»), это задача, даже если сейчас она в одну строку: завтра в неё добавится загрузка или откат.

**8.2. Стор хранит только данные:** поля, вычисляемые значения (`get`) и простые сеттеры. В сеттере нет условий, ограничений и каскадов: `setPage(page)` только присваивает, а проверку границ и сброс страницы при смене жанра делает задача. Запросы к API живут в задачах, debounce — в Presenter (8.9), отмена запроса — в `api/` (8.9.1). Ни таймеров, ни контроллеров в сторе нет.

**8.3. `observer` остаётся во View.** Он лишь подключает компонент к MobX и логикой не считается. Чтение наблюдаемых значений в `usePresenter` отслеживается, потому что хук вызывается во время рендера компонента-`observer`.

**8.4. Что допустимо в JSX.** Разрешены `.map()` и условный рендер по готовому значению из Presenter: `{isVisible && ...}`. Вычисления, форматирование и обработчики с логикой во View запрещены.

**8.4.1. Ранний выход тоже разрешён:** `if (!isVisible) return null;`. Это логика отображения, а не бизнес-логика: View лишь решает, рисовать ли себя, по готовому флагу из Presenter. Само условие (`pageCount > 1` и т. п.) по-прежнему вычисляет Presenter.

**8.5. Компоненту без логики Presenter не нужен.** Пустой `usePresenter` не создаём.

**8.6. Служебные папки пишутся строчными:** `logic`, `tasks`, `components`. С заглавной — только папки компонентов. В конспекте `Logic` и `Tasks`, смысл тот же.

**8.7. Код приведён к правилам урока 2 и раздела 9.** Номер оставлен, чтобы не сбить ссылки на следующие пункты. Если правила снова разойдутся с кодом, список расхождений ведём здесь.

**8.8. Глобальные папки клиента лежат в `src/`:**

- `src/api/` — общение с нашим сервером: запросы, типы ответов, ошибки транспорта (7.6);
- `src/stores/` — сторы-сущности и только они (8.2);
- `src/tasks/` — задачи, нужные нескольким компонентам (4.4);
- `src/components/` — компоненты, нужные во многих местах (4.1).

Папку создаём, когда в неё есть что положить. Пустые заготовки не нужны. Код сервера лежит в `server/` (раздел 9).

**8.9. Debounce — в Presenter.** Ждать паузу во вводе — это реакция интерфейса на ввод, а не сценарий. Presenter держит таймер (например, в `useRef`) и по истечении паузы вызывает задачу: `searchByTerm(term)`.

_Почему:_ задача остаётся обычной функцией без скрытого состояния между вызовами (7.1), а таймер исчезает вместе с компонентом, как локальное состояние в 7.5.

**8.9.1. Устаревший запрос отменяет `api/`.** Поиск запускают несколько задач: `searchByTerm`, `selectGenre`, `goToPage`. Все они вызывают `loadShows`, а та — `fetchShows`. «Одновременно идёт только один поиск» — свойство канала связи, поэтому `fetchShows` сам отменяет предыдущий запрос, а `abortFetchShows` отменяет текущий без нового (поле очистили). Задачи об `AbortController` не знают.

_Почему:_ у отмены должен быть один владелец, иначе запрос из пагинации не отменит запрос из поиска, и на экран попадёт устаревший ответ. Владельцем мог бы быть Presenter общего родителя, но тогда запуск запроса пришлось бы делать реакцией на стор, а это запрещает 7.8. Модуль `api/` один на всё приложение, а задача остаётся функцией без состояния (7.1).

**8.10. Задача возвращает код ошибки, текст ошибки делает Presenter.** Исключения из `api/` задача ловит сама и возвращает результат вида `{ error: "network" | "rate-limit" | "server" | null }`. Если ошибка нужна нескольким компонентам, тот же код кладётся в стор. Текст для пользователя («Проверьте интернет…») — это подготовка к отображению (1.2, 7.7), поэтому он живёт в `logic` компонента, который его показывает.

Отменённый запрос ошибкой не считается: `api/` бросает `AbortError`, задача распознаёт его через `isAbortError` из `api/client.ts`, тихо завершается и стор не трогает.

**8.11. Уведомление в сторе — это данные, а не текст.** Toast показывают разные компоненты, поэтому его состояние лежит в сторе: `toastStore.show("favorite-added", showName)`. Текст собирает Presenter компонента `Toast`, и таймер автоскрытия тоже живёт там. Правило то же, что для ошибок (8.10) и таймеров (8.2).

**8.12. Корневой `App` — каркас, а не начинка.** В нём только компонент верхнего уровня `Screens`: корпус телевизора и переключение каналов. Даже `Toast` живёт ниже, на кинескопе (`Screens/components/TvScreen/Toast`), потому что визуально это часть экрана. Загрузчики, навигация, прогрев и разметка экрана живут ниже, у тех компонентов, которым они нужны. Своего Presenter'а у `App` нет (8.5).

_Почему:_ корень читается как оглавление приложения (1.3). Когда в нём смешаны шапка, загрузка данных и переключение экранов, любое изменение одной части задевает остальные.

## 9. Frontend и backend

Раздел появился вместе с собственным сервером. В конспектах описания backend нет, это наше решение, сформулированное по тем же принципам: слои и ответственность (6.1).

**9.1. Бизнес-правила работы с данными живут на backend.** Фильтр по жанрам, пагинация, подсчёт жанров, кеш запросов к TVmaze и избранное — это правила, которые должны работать одинаково для любого клиента (веб, мобильное приложение). Поэтому они на сервере, а клиент передаёт только параметры: `term`, `genre`, `page`.

_Почему:_ если правило живёт на клиенте, второй клиент обязан его повторить и рано или поздно начнёт с ним расходиться. Плюс сервер видит все запросы и может их кешировать.

**9.2. Клиент не знает о TVmaze.** Внешний API — деталь сервера. Клиент ходит только в наш API, `src/api/` описывает его контракт. Если сервер сменит источник данных, клиент не изменится.

**9.3. Что остаётся на клиенте.** Задача на клиенте — это клиентский сценарий: вызвать `api/`, обновить стор, вернуть результат Presenter'у (7.5). Плюс всё, что зависит от интерфейса: debounce и отмена запроса (8.9), тексты ошибок и уведомлений (8.10, 8.11), форматирование (1.2), навигация (1.6). На сервер это не переносим: другому клиенту нужны свои тексты и своё поведение.

**9.4. Слои сервера повторяют слои клиента без View:**

```text
HTTP ──▶ routes ──вызов──▶ tasks ──▶ storage
           ▲                 │  └──▶ api/ (TVmaze)
           └───результат─────┘
```

- `routes/` — роль Presenter'а: разбирает запрос (query, params, body), вызывает задачу и превращает её результат в HTTP-ответ (статус, JSON). Бизнес-логики здесь нет.
- `tasks/` — бизнес-логика, правила раздела 7 действуют целиком. Вместо React (7.3) задача не знает об Express: никаких `req`, `res`, `next`, статусов HTTP. Задача получает обычные параметры и возвращает обычный результат с кодом ошибки (8.10).
- `storage/` — роль Entity: данные в памяти (`const cache = {}`, `const favorite = {}`) и простые синхронные методы чтения и записи. Правил здесь нет: срок жизни кеша проверяет задача, а не хранилище.
- `api/` — запросы к внешним сервисам (TVmaze), имена по 5.4: `fetchShows`, `fetchShow`.

**9.5. Структура папок сервера плоская по слоям.** У сервера нет дерева компонентов, поэтому правила 3.1–3.3 к нему не применяются. Задачи лежат в `server/src/tasks/`, большая задача становится папкой (3.5). Лимит в 120 строк (2.1) и правила именования (5.3, 5.4) действуют.

**9.6. Контракт между клиентом и сервером — JSON по HTTP.** Ошибки сервер отдаёт кодами (`{ error: "rate-limit" }`), а не текстами для пользователя: текст делает клиент (8.10). Типы ответа клиент описывает в `src/api/`, сервер — у себя. Общий пакет типов не заводим, пока расхождения не станут проблемой.

**9.7. Состояние сервера живёт в памяти процесса.** Баз данных пока нет: кеш и избранное пропадают при перезапуске. Поэтому сервер должен работать постоянно запущенным процессом, а не serverless-функцией, у которой память не переживает вызов.
