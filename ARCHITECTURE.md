# Правила архитектуры

Этот проект посвящён архитектуре, а не коду. Правила ниже обязательны для любого изменения. Если задачу нельзя решить по правилам, сначала обсуждаем правило, а не обходим его.

Источники: конспекты из [`conspects/`](conspects/). Новые правила после каждого урока добавляются сюда.

## 1. Слои

**1.1. View — только JSX.** View отвечает только за отображение. Единственная логика в нём — вызов хука `usePresenter`.

**1.2. Presenter — прослойка между данными и View.** Presenter извлекает данные из хранилища и готовит их к отображению. View получает готовые значения и обработчики.

**1.3. Логика живёт в хуках с понятными именами.** Presenter не должен разрастаться: отдельные задачи выносятся в отдельные хуки, например `useSuggestions`. Код читается как оглавление книги: сначала абстракции, детали скрыты внутри.

## 2. Размер файлов

**2.1. Не больше 120 строк в любом файле.** Если файл не помещается в лимит, его разбивают на более мелкие абстракции. Исключений нет.

## 3. Структура папок

**3.1. Дерево папок повторяет иерархию компонентов на экране.**

**3.2. У каждого компонента своя папка**, в которой лежат его view и presenter.

**3.3. Компонент, используемый только внутри другого компонента, лежит в папке родителя.** Глубина вложенности не ограничена: 10–15 уровней — это нормально.

```text
Messenger/
├── Chats/
└── ActiveChat/
    └── BottomPanel/
        └── StickerPackIcon/
```

## 4. Переиспользуемые компоненты

**4.1. Компонент, нужный во многих местах приложения, лежит в глобальной папке `components`.** Например, инпуты и модальные окна.

**4.2. Компонент, переиспользуемый только в одной ветке дерева, лежит в промежуточной папке `components` этой ветки.** Такая папка допустима на любом уровне. При удалении ветки вместе с ней уходят и её компоненты.

## 5. Именование

**5.1. Файл View называется так же, как его папка:** `SearchBar/SearchBar.tsx`.

**5.2. Файл Presenter называется `usePresenter.ts`:** `SearchBar/usePresenter.ts`.

## 6. Принципы

**6.1. Архитектура — это абстракции, а не инструменты.** Решения формулируем через слои и ответственность, а не через конкретные библиотеки.

**6.2. Правила не ослабляем ради скорости.** Большой файл быстрее написать, но дороже поддерживать.

**6.3. Правила проверяем практикой.** Вопрос, возникший при применении правила, обсуждаем и фиксируем здесь.

## 7. Применение в этом проекте

Эти пункты не из конспекта: они уточняют правила под наш стек.

**7.1. Хранилище — MobX.** Конспект говорит о Redux, у нас его роль играют MobX-сторы. Читать стор и вызывать его действия может только Presenter, но не View.

**7.2. `observer` остаётся во View.** Он лишь подключает компонент к MobX и логикой не считается. Чтение наблюдаемых значений в `usePresenter` отслеживается, потому что хук вызывается во время рендера компонента-`observer`.

**7.3. Что допустимо в JSX.** Разрешены `.map()` и условный рендер по готовому значению из Presenter: `{isVisible && ...}`. Вычисления, форматирование и обработчики с логикой во View запрещены.

**7.4. Компоненту без логики Presenter не нужен.** Пустой `usePresenter` не создаём.
